3. All 9 Layers Explained

Each layer includes: what it is, a real-world analogy, an example from YOUR project, and the AI engineering concepts it introduces.

1 Harness (The Agent Loop)

The harness is the execution loop that lets an LLM act in the real world. Without it, an LLM just answers questions. With it, the LLM can plan steps, use tools, observe results, and decide what to do next.

Analogy: A chef reading a recipe vs. actually cooking. The recipe is the LLM's knowledge. The kitchen (stove, pans, ingredients) is the harness. Without the kitchen, the chef just talks about food.
Example: Claude Code itself IS a harness. It takes your message, lets Claude reason, call tools (Read, Edit, Bash), observe results, and decide the next step. The Workflow tool is a multi-agent harness.
In QA Forge: The Orient → Plan → Act → Verify → Heal loop. The agent doesn't just generate test code — it runs it, sees the failure, fixes it, and retries.

Concepts introduced:

Agent Loop / ReAct Pattern
A cycle of Reason → Act → Observe, repeated until the task is done.
Agent thinks "I need to find the button locator" (Reason) → navigates to OperatorHub via Playwright (Act) → sees the DOM structure (Observe) → "OK, the locator is data-test="search-operatorhub"" (Reason) → writes it to code (Act)
Tool Use / Function Calling
The LLM doesn't browse the web or run code itself. It outputs a structured "tool call" (like a function call), the harness executes it, and returns the result.
Claude outputs: {"tool": "Bash", "command": "pytest tests/"}. Claude Code runs it and gives Claude the stdout/stderr. Claude never touched the terminal directly.
2 Memory & State

State is what the agent is doing RIGHT NOW (current task, steps completed). Memory is what it remembers ACROSS tasks (past failures, learned conventions). Without memory, the agent makes the same mistakes every time.

Analogy: State = the page your book is open to. Memory = all the books you've ever read. A new conversation with Claude starts with a blank state, but memory lets it recall "last time I tried that locator, it failed."
Example: Your .claude/projects/.../memory/ directory is persistent memory. It survives across conversations. The messages in your current chat are state — they disappear when the context fills up.
In QA Forge:
State: "I'm on heal attempt 2/3 for the Tasks list page test"
Memory: .agent/memory/locator_registry.json stores verified locators per version so the agent never guesses locators it has already verified.

Concepts introduced:

Context Window
The LLM's "working memory" — how much text it can see at once. Claude's context window is ~200K tokens. Anything outside it is invisible to the model.
If your conversation gets too long, older messages get compressed or dropped. That's why we need persistent file-based memory — the context window is temporary, files are permanent.
Token
The unit LLMs process. Roughly 1 token = 0.75 words. "Hello world" = 2 tokens. A 500-line Python file ≈ 2,000 tokens. You pay per token (input + output).
Claude Sonnet costs ~$3/million input tokens, $15/million output tokens. A 10-step agent run might use 50K-200K tokens total. Context management (what you put in the prompt) directly affects cost.
Prompt Caching
Reusing previously processed prompt content to save time and money. If you send the same system prompt repeatedly, the provider caches it so only new content is processed.
Claude Code uses a 5-minute cache TTL. If you respond within 5 minutes, the previous context is cached (faster + cheaper). After 5 minutes, it reprocesses everything.
3 RAG (Retrieval-Augmented Generation)

RAG means: before the LLM generates an answer, it retrieves relevant documents and includes them in the prompt. This way the LLM answers based on YOUR data, not just its training data.

Analogy: Imagine an exam where you're allowed to bring a cheat sheet. RAG is the cheat sheet — the student (LLM) is smart, but the cheat sheet (retrieved docs) ensures they give answers specific to YOUR course, not generic textbook answers.
Example: Your bdd-test-code-generator skill queries NotebookLM (notebook_query) to get Tekton-specific knowledge before generating tests. That's RAG — retrieving product docs at generation time.
In QA Forge: 4-tier retrieval priority:
1. Locator Registry (verified) → 2. Framework codebase (grep) → 3. Product docs (NotebookLM) → 4. Live UI extraction (Playwright)
The agent tries the fastest, most reliable source first. Only hits the live UI if nothing else has the answer.

Concepts introduced:

Hallucination
When the LLM confidently generates something that looks correct but is factually wrong. LLMs are pattern completers — they predict what text SHOULD come next, not what's TRUE.
Claude generates data-test="pipeline-create-btn" because it looks right based on patterns. But the actual element is data-test="item-create". That's a hallucinated locator.
Grounding
Connecting the LLM's output to real, verifiable data sources. The opposite of hallucination. RAG is a grounding technique.
Instead of guessing the locator, the agent navigates to the page via Playwright, extracts the actual DOM, and uses the REAL data-test attribute. That's grounding — the locator comes from reality, not imagination.
Embedding / Vector Search
A way to find "similar" content. Text is converted to numbers (vectors), and math finds the closest match. Not all RAG uses this — keyword search works too.
NotebookLM uses embeddings internally. When you query "Tekton Task YAML structure", it finds the most semantically similar paragraphs in your uploaded docs, even if they don't contain those exact words.
4 MCP (Model Context Protocol)

MCP is a standard interface for connecting LLMs to external tools and data sources. Think of it as USB for AI — one plug that works with any tool, any model.

Analogy: Before USB, every device had its own cable (printer cable, mouse cable, keyboard cable). USB standardized the plug. Before MCP, every AI tool had its own integration code. MCP standardizes how AI talks to tools.
Example: Your Playwright MCP server exposes tools like browser_navigate, browser_snapshot, browser_click. Claude doesn't need to know HOW Playwright works — it just calls the MCP tool and gets the result.
In QA Forge:
Playwright MCP = eyes (see the UI)
File System = hands (write code)
Shell/CLI = voice (run commands)
NotebookLM MCP = library card (look up product knowledge)

Concepts introduced:

Tool Schema
A structured description of what a tool does, what parameters it accepts, and what it returns. The LLM reads this to know WHEN and HOW to use the tool.
{"name": "browser_click", "params": {"selector": "string"}, "description": "Click an element on the page"} — Claude reads this schema and knows it can call this tool with a CSS selector.
MCP Server vs Client
The MCP Server provides tools (e.g., Playwright exposes browser actions). The MCP Client uses tools (e.g., Claude Code calls those browser actions). One server can serve many clients.
Your Playwright MCP server runs as a process. Both Claude Code AND Cursor can connect to it as clients. Same tools, different IDEs. That's the "agnostic" part.
5 Skills (Reusable Know-How)

A skill is a packaged set of instructions saved as a file. Only the name and description are loaded into context — the full instructions load only when the skill is invoked. This saves tokens.

Analogy: A recipe book's table of contents vs. the full recipe. You scan the titles (cheap — small context). Only when you decide to cook "Pasta Carbonara" do you open that page (load full skill). You don't read every recipe every time you enter the kitchen.
Example: Your .claude/skills/bdd-test-code-generator/ has a main skill file plus references. When you type /bdd-test-code-generator, only THEN does the full skill load. Otherwise Claude just sees the one-line description.
In QA Forge: Skills are organized by agent loop phase:
orient/ — intent-parser, page-discoverer
act/ — locator-extractor, test-generator
verify/ — test-runner, locator-verifier
heal/ — failure-classifier, locator-healer
learn/ — pattern-recorder, locator-updater

Concepts introduced:

Progressive Disclosure
Only loading detailed information when it's needed. Saves context window space and money. Critical for keeping agent costs manageable.
CLAUDE.md loads every turn (keep it small!). Skills load on-demand. References load when a skill says "read this file." Three tiers of detail, each loaded only when needed.
System Prompt / Instructions
The hidden instructions sent to the LLM before your message. They define the LLM's behavior, personality, and rules. You don't see them, but they shape every response.
CLAUDE.md content becomes part of the system prompt. Skills become part of it when invoked. The agent's "personality" (how it writes tests, what conventions it follows) lives here.
6 Guardrails

Guardrails are safety boundaries that prevent the agent from doing harmful things. They're the difference between a demo that impresses and a production system that's trustworthy.

Analogy: A self-driving car has guardrails: speed limits, lane boundaries, emergency braking. The car is smart enough to drive, but without guardrails it might drive off a cliff while "optimizing the route."
Example: Claude Code's permission system is a guardrail. When a tool is risky (writing files, running commands), it asks you before proceeding. The .claude/settings.json allowlist controls which tools run automatically.
In QA Forge:
• Max 3 heal retries (prevents infinite loops)
• Only modify files under tests/ and framework/ (blast radius)
• Test must pass 3/3 runs before marking done (stability gate)
• If the failure looks like a real product bug, STOP and report (don't mask bugs)
• Token budget per task (cost control)

Concepts introduced:

Blast Radius
How much damage an agent can do if something goes wrong. Smaller blast radius = safer. Achieved by limiting what files/systems the agent can touch.
QA Forge can write to tests/ and framework/locators/. It CANNOT modify conftest.py, CI configs, or core framework code. If it goes haywire, the damage is contained.
Escalation
When the agent recognizes it can't solve the problem and hands control to a human instead of blindly retrying.
After 3 failed heal attempts, QA Forge stops and says: "I tried X, Y, Z. None worked. The failure appears to be [analysis]. Here's what I'd try next, but I need a human to decide."
Human-in-the-Loop (HITL)
A design pattern where a human reviews and approves critical decisions before the agent proceeds. Can be "always" (approval gate) or "sometimes" (escalation only).
Your current bdd-test-code-healer has an approval gate (HITL always). QA Forge removes HITL for the happy path but keeps it for escalation (HITL sometimes). The goal is zero intervention for routine tasks.
7 Evals (Measuring Quality)

Evals are automated tests for your AI. They measure whether the agent's output is good. Without evals, you're flying blind — you don't know if the agent is improving or getting worse over time.

Analogy: Evals are to AI what unit tests are to code. You wouldn't ship code without tests. Don't ship an agent without evals. The agent writes tests for your product — evals are the tests for the agent itself.
Example: After the agent generates a test, the eval checks: Did all locators resolve to real elements? Did the test pass 3/3 runs? Does the code follow your naming conventions? Each gets a score.
In QA Forge:
EvalWhat it measuresTarget
Locator accuracy% of locators that work first try> 90%
First-pass success% of tests passing without healing> 70%
Heal success rate% of failures fixed in 3 tries> 85%
Stability score% passing 3/3 consecutive runs> 95%
Convention compliance% matching framework patterns> 95%

Concepts introduced:

Eval / Evaluation
A test that scores AI output quality. Unlike unit tests (binary pass/fail), evals often produce scores (0-100) or grades (A-F). They can be automated or human-judged.
"Did the locator resolve?" is a binary eval. "How readable is the generated code?" is a scored eval (LLM-as-judge, where a second LLM scores the first one's output).
LLM-as-Judge
Using one LLM to evaluate another LLM's output. Cheaper and faster than human review, but less reliable. Good for scoring code quality, convention compliance, etc.
After QA Forge generates a test, a separate Claude call reviews: "Does this code follow the framework's POM pattern? Score 1-10." This is the judge scoring the worker.
Regression (in AI context)
When the agent used to do something well but stops doing it well. Evals catch regressions. Example: after adding a new skill, locator accuracy drops from 92% to 78%.
Week 1: 90% locator accuracy. Week 3: 75%. The eval trend shows something broke. Without evals, you'd only notice when tests start failing in CI.
8 A2A (Agent-to-Agent Protocol)

A2A is a standard way for agents from different vendors to communicate. Like how HTTP lets any browser talk to any web server, A2A lets any agent hand off work to any other agent.

Analogy: Email. You use Gmail, your colleague uses Outlook. Different vendors, but the email protocol (SMTP) lets you communicate. A2A is SMTP for AI agents.
Example: QA Forge generates tests. A separate "CI Agent" (maybe built by another team) runs them across 5 browser configurations. QA Forge hands off via A2A: "Here's the test file, run it on Chrome, Firefox, Safari."
In QA Forge: Not needed day one. Design for it by using standard I/O (JSON task files). When you're ready, A2A lets QA Forge talk to a CI agent, a code review agent, or a monitoring agent — even if they're built with different tools.

Concepts introduced:

Agent Card (A2A)
A JSON file that describes what an agent can do, what inputs it accepts, and what outputs it produces. Other agents read this to know if/how to hand off work.
{"name": "qa-forge", "skills": ["test-generation", "test-healing"], "input": "test-intent-string", "output": "test-results-json"}
9 Multi-Agent (Parallel Specialists)

Instead of one agent doing everything, split the work among specialist agents coordinated by an orchestrator. Each specialist is simpler, faster, and better at its narrow task.

Analogy: A hospital. The receptionist (orchestrator) routes you to the right specialist (cardiologist, dermatologist). Each specialist is world-class at their one thing. Better than one "general doctor" trying to do everything.
Example: Claude Code's Agent tool spawns sub-agents. The Workflow tool runs multiple agents in parallel. Your /bdd-test-code-generator could spawn a locator-extraction agent and a test-data-generation agent simultaneously.
In QA Forge (batch mode):
Orchestrator receives: "Generate tests for all 5 Task pages"
Spawns 5 parallel agents, one per page
Each: extract locators → generate test → run → heal
Orchestrator merges results, deduplicates shared step definitions

Concepts introduced:

Orchestrator
The "boss" agent that breaks a big task into smaller tasks and assigns them to specialist agents. It doesn't do the work itself — it coordinates.
QA Forge orchestrator: "Task 1: Extract locators for Tasks page (send to Locator Agent). Task 2: Generate test data (send to Data Agent). Task 3: Wait for both, then generate test code."
Fan-out / Fan-in
Fan-out: splitting one task into many parallel sub-tasks. Fan-in: collecting all results back together. The orchestrator does both.
Fan-out: "Extract locators from 5 pages" → 5 parallel agents. Fan-in: Collect all 5 locator sets, merge into one registry, resolve conflicts.
Pipeline vs DAG
Pipeline: steps run one after another (A → B → C). DAG (Directed Acyclic Graph): steps can run in parallel when they don't depend on each other (A → B+C → D).
Pipeline: extract locators → generate test → run test. DAG: (extract locators + generate test data) in parallel → generate test → run test. DAG is faster because independent steps overlap.

  |  Concept: FAILURE CLASSIFICATION                                       |
  |  Don't apply the same fix to every error. A locator error needs         |
  |  re-extraction. A timing error needs longer waits. A data error         |
  |  needs YAML fixes. A logic error needs code changes.                    |
  |  A REAL BUG needs human reporting, not agent fixing.                    |
  └─────────────────────────────────────────────────────────────────────────┘
    |
    v
  ┌─────────────────────────────────────────────────────────────────────────┐
  | LEARN (Remember for next time)                                        |
  |                                                                         |
  |  1. Save verified locators to registry (with version + timestamp)       |
  |  2. If healed: save failure pattern --> fix mapping                     |
  |  3. Update eval scores (locator accuracy, first-pass rate)              |
  |  4. If human corrected: save convention to memory                       |
  |                                                                         |
  |  Concept: LOOP ENGINEERING / FLYWHEEL                                  |
  |  Every task makes the agent better at the NEXT task.                    |
  |  More verified locators = fewer hallucinated locators.                  |
  |  More failure patterns = faster healing.                                |
  |  More conventions = better code on first try.                           |
  |                                                                         |
  |  This is the difference between an agent that stays dumb                |
  |  and one that gets smarter over time.                                   |
  └─────────────────────────────────────────────────────────────────────────┘

6. AI Engineering Glossary (A-Z)

Every term used in QA Forge, explained simply with examples from your project.

A2A (Agent-to-Agent)
An open standard for agents to discover each other and hand off tasks, regardless of vendor.
QA Forge (Claude-based) hands test results to a CI Agent (maybe GPT-based). A2A makes cross-vendor handoffs possible.
Agent
An LLM + tools + a loop. It can plan, act, observe, and decide. An assistant answers questions. An agent completes tasks.
ChatGPT answering "how do I test this?" = assistant. QA Forge writing the test, running it, fixing failures, and committing = agent.
Agent SDK
A software library for building agents as code. Handles the loop, tool calling, and state management so you don't build it from scratch.
Claude Agent SDK (Python/TS) lets you define: agent name, system prompt, tools, and loop behavior. Then agent.run("write a test") does the rest.
Chain of Thought (CoT)
Making the LLM "think step by step" before giving an answer. Improves accuracy on complex tasks.
"First, identify the page. Then, check for existing locators. Then, extract missing ones. Then, generate code." Each step builds on the previous one.
Confidence Score
A number (0 to 1) indicating how sure the agent is about something. Used to decide whether to proceed or ask for help.
Locator verified on live UI = 0.95. Locator from docs only = 0.5. Locator guessed = 0.3. Threshold: don't use anything below 0.7.
Context Window
The maximum amount of text (tokens) an LLM can process in one request. Claude = ~200K tokens. Everything outside is invisible.
If you paste a 10,000-line file and ask about line 1, Claude might "forget" the details of line 9,500. Context management = keeping important stuff visible.
Decomposition
Breaking a complex task into smaller sub-tasks that are easier to solve individually.
"Write a test for Task CRUD" decomposes into: generate test data + extract locators + write POM methods + write steps + write feature.
Embedding
Converting text into a list of numbers (vector) that captures meaning. Similar texts have similar vectors. Used for search.
"create a pipeline" and "make a new pipeline" have very different words but similar embeddings, so a vector search finds both.
Escalation
The agent stops and asks a human when it can't solve a problem or when confidence drops too low.
After 3 failed heal attempts: "I can't fix this. The error suggests the Cancel button was removed in v4.22. Is this a UI change or a bug?"
Eval (Evaluation)
A test that measures AI output quality. The "unit tests" for your agent.
Locator accuracy eval: run 100 locator extractions, check what % match real elements. Target: >90%.
Fan-out / Fan-in
Fan-out: split one task into many parallel tasks. Fan-in: collect results. The orchestration pattern for multi-agent.
Fan-out: extract locators from 5 pages simultaneously. Fan-in: merge 5 locator sets into one registry file.
Flywheel / Loop Engineering
A self-reinforcing cycle where each task's output improves the next task's input. The agent gets better by doing.
Run 1: extract 20 locators, 15 correct (75%). Save all to registry. Run 2: 15 come from registry (100% correct), only 5 need extraction. Overall accuracy rises.
Grounding
Connecting LLM output to verifiable real-world data. Prevents hallucination.
Instead of Claude imagining what the button's data-test attribute is, Playwright MCP navigates to the page and reads the actual DOM. That's grounding.
Guardrails
Safety boundaries: what the agent CAN'T do, limits on retries, human approval gates, file access restrictions.
QA Forge guardrail: "Never delete an existing passing test." Even if the agent thinks it should, the guardrail blocks it.
Hallucination
The LLM generates something that looks correct but is factually wrong. It's "pattern completing" not "truth telling."
Claude writes [data-test="create-pipeline-btn"] because it looks like the right CSS selector pattern. But the real attribute is [data-test="item-create"].
Harness
The infrastructure that wraps around the LLM: the loop, tool execution, state management, error handling.
Claude Code is a harness. The Agent SDK is a harness builder. QA Forge's Orient-Plan-Act-Verify-Heal loop is a custom harness.
Human-in-the-Loop (HITL)
A human reviews and approves before the agent takes action. Can be "always" or "only on escalation."
Current: agent proposes a fix, you type "yes" to apply. Goal: agent fixes automatically, only asks human after 3 failures.
LLM (Large Language Model)
The AI model (Claude, GPT, etc.). Trained on internet text. Good at: understanding language, writing code, reasoning. Bad at: knowing YOUR specific product.
Claude knows Python, knows Playwright, knows Tekton concepts. But it doesn't know that YOUR OperatorHub card has data-test="openshift-pipelines-operator-rh-custom-operators-openshift-marketplace".
LLM-as-Judge
Using one LLM call to evaluate another's output. Faster and cheaper than human review for routine quality checks.
After generating test code, a second Claude call scores it: "Convention compliance: 9/10. Missing: logger import. Locator pattern: correct."
MCP (Model Context Protocol)
A standard for connecting LLMs to tools. Like USB for AI. One protocol, any tool, any model.
Playwright MCP exposes browser_click(selector). Claude calls it through MCP. Tomorrow you could swap Claude for another model and the MCP tools still work.
Multi-Agent
Multiple specialized agents working together, coordinated by an orchestrator. Each agent is expert at one thing.
Locator Agent (extracts DOM), Test Writer Agent (generates code), Healer Agent (fixes failures). Better than one agent doing everything.
Orchestrator
The "boss" agent that breaks tasks into sub-tasks and assigns them to specialist agents.
QA Forge orchestrator: "Page 1 → Agent A, Page 2 → Agent B, Page 3 → Agent C. When all done, merge results."
Progressive Disclosure
Only loading information when needed. Saves context window space and cost.
Skill description loads always (1 line). Skill body loads on invoke (50 lines). Skill references load when the skill says to (200 lines). Three tiers.
Prompt Engineering
Crafting the instructions you give to an LLM to get the best output. Includes system prompts, few-shot examples, formatting instructions.
Your CLAUDE.md is prompt engineering. Your skills are prompt engineering. The way you phrase "write a test" matters: "Write a BDD test using Scenario Outline with Examples table for Task creation" gets better output than "write a test for tasks."
RAG (Retrieval-Augmented Generation)
Retrieve relevant documents first, then generate with them in context. The LLM answers based on YOUR data, not just training data.
Before generating a Task YAML, query NotebookLM: "What are required fields for a Tekton Task?" The response goes into the prompt, so Claude uses YOUR docs, not generic knowledge.
ReAct Pattern
Reason → Act → Observe, repeated. The standard agent loop. Named after a 2022 research paper.
Reason: "I need the Create button locator." Act: Navigate to Tasks page via Playwright. Observe: Snapshot shows data-test="item-create". Reason: "Got it, now I'll write the locator class."
Skill
A saved set of instructions that the agent loads when a specific type of task is detected. Like a checklist for a specific procedure.
/bdd-test-code-generator is a skill. It has specific steps, references, and examples. It loads only when test generation is needed.
Temperature
Controls randomness in LLM output. 0 = deterministic (same input → same output). 1 = creative (same input → different outputs each time).
For code generation: low temperature (0-0.2) — you want consistent, predictable code. For brainstorming test scenarios: higher temperature (0.5-0.7) — you want creative ideas.
Token
The unit LLMs process text in. ~1 token = 0.75 words = ~4 characters. LLMs have a max token budget per request.
"Hello, world!" = 4 tokens. A 200-line Python file ≈ 1,000 tokens. Claude's 200K context = roughly 150,000 words.
Tool Use / Function Calling
The LLM can't directly run code, browse the web, or read files. Instead, it outputs a "call this tool with these parameters" instruction. The harness executes it.
Claude outputs: Read(file="/framework/locators/tasks.py"). Claude Code reads the file and shows Claude the content. Claude never touched the filesystem itself.

7. Build Phases

Ordered by impact. Each phase delivers a working improvement.

Phase A: Locator Grounding (Week 1)

Wire Playwright MCP into the test generation flow. Every locator is extracted from the live UI and verified before use. Save verified locators to a registry file.

Impact: Fixes ~70% of locator hallucination. The single biggest improvement.

Concepts used: Grounding, MCP, Confidence Score, Progressive Disclosure

Phase B: Persistent Memory (Days 2-4)

Build the locator registry, failure pattern store, and convention memory. Agent remembers verified locators and past fixes across sessions.

Impact: Second-time locator extraction drops to zero (cached). Heal time drops because patterns are recognized.

Concepts used: Memory, Flywheel, Loop Engineering

Phase C: Autonomous Loop (Week 2)

Wire generator → runner → healer into one continuous loop. Remove approval gates for routine operations. Keep escalation for edge cases.

Impact: Zero human intervention for standard test generation.

Concepts used: Agent Loop, ReAct, Guardrails, Escalation, HITL

Phase D: Smart Healing (Week 3)

Build the failure classifier. Different fix strategies for locator errors vs timing errors vs data errors vs real bugs.

Impact: Heal success rate jumps from ~60% to ~85%. Stops masking real product bugs.

Concepts used: Failure Classification, Chain of Thought, Confidence Score

Phase E: Evals & Quality Tracking (Week 3-4)

Build the eval framework. Track locator accuracy, first-pass success, heal rate over time. Alert when quality drops.

Impact: Know exactly how good the agent is. Catch regressions early.

Concepts used: Eval, LLM-as-Judge, Regression Detection

Phase F: Portability (Week 4-5)

Package as a Claude Agent SDK agent. Same agent definition works in Claude Code (native), Cursor (MCP), and standalone (API).

Impact: Tool-agnostic. Not locked to any IDE.

Concepts used: Agent SDK, MCP, Tool Schema

Phase G: Multi-Agent & Batch (Week 5-6)

Orchestrator + specialist agents for batch operations. Fan-out across pages, fan-in results.

Impact: "Generate tests for all 10 pages" runs in parallel, not sequentially.

Concepts used: Multi-Agent, Orchestrator, Fan-out/Fan-in, DAG, A2A
